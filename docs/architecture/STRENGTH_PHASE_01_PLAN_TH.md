# STRENGTH_PHASE_01: แผนให้เอนจิ้นแกร่งขึ้นชัดเจน (+50 ถึง +100 Elo)

ร่าง 2026-10-15 ตามคำขอเจ้าของ: "เอนจิ้นที่แกร่งขึ้นแบบชัดเจน ขั้นต่ำ +50–100 Elo
แพ้ยากขึ้นมาก ชนะในตำแหน่งที่ได้เปรียบ และประเมินหมากเก่งขึ้นแบบเห็นได้ชัด"
สถานะ: **อนุมัติ 2026-10-15** (เจ้าของ: "ตกลงทั้ง 4 ข้อ เริ่มตามแผนเลย" — Q1–Q4 ตามคำแนะนำ) ไม่มีอะไรในเอกสารนี้เปลี่ยน production,
accepted DLL, `RULESET.json` หรือ `makhos/core.py`

ตัวเลข Elo ในข้อ 2 แยกเป็น [วัดแล้ว] กับ [ประเมิน] การประเมินไม่ใช่สัญญา
เกณฑ์จบ phase ในข้อ 1 ประกาศก่อนวัด และห้ามแก้เพื่อให้ผ่าน

จึงเสนอเป็นการตัดสินใจแยก (ข้อ 5 DP3, ข้อ 7 Q3)

## 3. ข้อเท็จจริงจาก part A ที่กำหนดทิศทาง

- **แปลงความได้เปรียบใหญ่ได้ดีอยู่แล้ว:** คะแนนตัวเอง ≥ +300 สองครั้งติด →
  ชนะ 96.7% (1,422 จาก 1,470) ส่วนที่ tablebase บอกว่าชนะ แปลงได้ 1,402/1,402
- **ช่วงที่เสียเกมคือต้น–กลางเกม:** การทรุดหลังตาที่ 20–29 มี 52% และตา 10–29 มี 76%
  ก่อนทรุดเอนจิ้นประเมินว่าเท่ากัน (ใกล้ 0) ที่ depth ประมาณ 19 และ 80% ของคำตอบที่ทำให้ทรุดเป็นตาเงียบ
  → ปัญหาคือการประเมินตำแหน่งและ horizon ในช่วงกลางเกม ตรงกับจุดอ่อนของ v1
- **ได้เปรียบเล็กน้อยยังแปลงได้ไม่ดี:** +100 ถึง +200 ภายในตา 40 → ชนะ 59%
  เสมอ 36% แพ้ 5% นี่คือพื้นที่ของ G5
- part A วัดที่ประมาณ 0.3 วินาทีต่อตา ไม่ใช่ 10 วินาทีต่อตา

## 4. งานและลำดับ

หลักการ: gate หนักรันทีละตัว (เครื่อง 6C/12T เครื่องเดียว) งานเบาทำคู่ขนานได้
ทุก gate รันแบบ detached BelowNormal

### Track A: การค้นหา (critical path)

1. **A1** จบ NULL_EVAL_01 W2 (กำลังรัน ประมาณ 1 วันถ้าไปถึงเพดาน)
2. **A2** HISTORY_MALUS_01 W1 (1T, 10s+0.1s, H0=0/H1=+2, cap 4,000) ประมาณ 1 วัน
3. **A3** สร้าง SEARCH_INT_01 (งานเบา ทำระหว่าง A1/A2): รวม 3 diff native เล็ก ๆ
   (+15, +90, +41 บรรทัดใน `native/makhos_native.c`) บน strict key ที่อยู่ใน `main` แล้ว
   build DLL ใหม่ พร้อม perft 10 + differential + full suite ตัด HISTORY_MALUS ออก
   ถ้า A2 FAIL
4. **A4** SEARCH_INT_01 vs production: W1 (1T, H0=0/H1=+5 เพราะคาดผลใหญ่) แล้ว W2
   (12T fixed 1 s) ประมาณ 1–2 วันรวม

### Track B: NNUE v2-A (ตามสัญญาข้อมูลที่ freeze แล้ว)

1. **B1** (เบา ทำได้ทันที) exact-WDL probe + การตรวจสร้างข้อมูลซ้ำแบบไบต์ตรงกัน
2. **B2** สร้างข้อมูล 10M แถว 5 workers ประมาณ 1–1.5 วัน ไม่รันพร้อม gate
3. **B3** freeze trainer contract → เทรน → quantize → parity Python/scalar/AVX2 →
   sealed report ครั้งเดียว (G6) ประมาณ 2–3 วัน
4. **B4** v2-A screen + W1 vs v1 (บนการค้นหา production) ประมาณ 1.5–3 วัน

### Track C: แพ้ยากขึ้น

1. **C1** (เบา–กลาง) ชุด "collapse suite" 781 ตำแหน่งจาก part A: ค้นซ้ำด้วย production,
   SEARCH_INT_01 และ safety mode ที่งบเวลาเท่ากัน แล้วเทียบกับการค้นหาอ้างอิงที่ลึกกว่า
   วัดว่าตาที่ทำให้ทรุดถูกเลี่ยงได้กี่ % ใช้ตัดสินว่า safety mode คุ้มทำ SPRT ไหม
2. **C2** safety mode: screen + W1 บนพื้น SEARCH_INT_01 เฉพาะถ้า C1 แสดงว่าช่วย
3. **C3** (หลัง RC-2) opening book ระยะสั้นจาก opening ที่แพ้บ่อยใน part A
   ติดป้าย "ตรวจด้วยการค้นลึกที่ depth/เวลา X" ไม่ใช่ "ดีที่สุดแน่นอน" ค่าเริ่มต้นปิด

### ประกอบและยืนยัน

1. **R1** RC-2 = SEARCH_INT_01 + NNUE ที่ดีกว่า (v2-A ถ้าผ่าน B4 ไม่งั้น v1)
   + safety mode ถ้าผ่าน C2
2. **R2** G1 (2,000 คู่ 1T) → G2 (1,000 คู่ 12T) → G4 (self-play ซ้ำ) → G7
3. **R3** เจ้าของตัดสินใจขึ้น production พร้อม rollback

## 5. จุดตัดสินใจระหว่างทาง

- **DP1 หลัง A4 W1:** ถ้า SEARCH_INT_01 vs production < +30 Elo → ablation (ถอดทีละตัว)
  ก่อนไปต่อ เพราะแปลว่าองค์ประกอบตีกันเอง
- **DP2 หลัง B4:** ถ้า v2-A ไม่ผ่าน → RC-2 ใช้ v1 และย้าย output buckets (v2-B) หรือ
  ข้อมูลรอบสองไป phase ถัดไป
- **DP3 หลัง G1/G2:** ถ้า 1T ผ่าน +50 แต่ 12T ต่ำกว่า +30 → คอขวดคือ SMP เสนอ SMP track
  แยกให้เจ้าของตัดสินใจ
- **DP4 ถ้า G1 < +50:** ไม่ลดเกณฑ์ ไปคันโยกถัดไปตามหลักฐาน: v2-B output buckets
  (เล็งช่วง 9–12/5–8 ตัว), ข้อมูลรอบสองที่ใช้ RC-2 เป็น teacher, หรือ SMP

## 6. ความเสี่ยง

1. ผลของตัวเลือกการค้นหาอาจไม่บวกกัน และทั้งหมดวัดบน strict key ที่ยัง INCONCLUSIVE
   → แก้ด้วยการวัด SEARCH_INT_01 กับ production โดยตรง (A4)
2. ผลที่ 1T อาจไม่ย้ายไป 12T → W2 และ G2 วัดแยก
3. NNUE v2-A อาจได้น้อย (เอกสารร่าง V2 เดิมประเมิน +5–20) → ไม่ได้พึ่งมันเป็นก้อนหลัก
4. การขัดจังหวะของเครื่อง (Windows Update, อัปเดตแอป) → รันแบบ detached + resume จาก checkpoint
5. self-play เสมอมากขึ้นไม่รับประกันว่าแรงขึ้น และกลับกัน → ใช้ G1/G2 เป็นเกณฑ์หลัก

## 7. คำถามที่ต้องให้เจ้าของตัดสินใจ

  ทีเดียว (ประหยัดประมาณ 3 วันเครื่อง) — แนะนำ: ใช่
