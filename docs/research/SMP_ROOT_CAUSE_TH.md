## 2. สาเหตุ (เรียงตามน้ำหนัก)

production ที่ 12T ใช้ `ParallelNativeSearch` ใน `makhos/parallel_native.py`
คือ root split ที่ Python เป็นตัวคุม ไม่ใช่ SMP ในตัวเอนจิ้น

1. **ทุกตาที่ root ถูกค้นแบบ full window**
   เอนจิ้น 1 เธรดใช้ PVS: ค้นตาแรกเต็ม แล้วค้นตาที่เหลือแบบ null window รอบคะแนนของตาแรก
   ซึ่งส่วนใหญ่ตกทันที (fail low) ด้วยต้นทุนต่ำ
   root split ส่งแต่ละตาไปให้ worker ค้นด้วย `worker.search(child, depth=d-1)` แบบเต็มหน้าต่าง
   ทุกตาจึงแพงเท่ากับตาหลัก นี่คือที่มาของ node 3.4–4.3 เท่า ซึ่งกินกำไรจากเธรดเกือบหมด
2. **รอกันทุก depth และตาที่ root มีน้อย**
   depth หนึ่งจะนับก็ต่อเมื่อทุกตาค้นจบ จึงต้องรอตาที่ช้าที่สุดทุกรอบ
   จาก corpus `middlegame_search_v5` (960 ตำแหน่ง) จำนวนตาที่ root มีค่ามัธยฐาน 7, 36% มีไม่เกิน 6 ตา, 8% มีแค่ 2 ตา
   12 เธรดจึงทำงานพร้อมกันได้ไม่เกินจำนวนตา และส่วนใหญ่ว่างระหว่างรอ
3. **TT แยกต่อ worker**
   hash 512 MiB ถูกแบ่งเป็น 12 ส่วน (`hash_power_for_megabytes(..., partitions=...)`)
   subtree ของแต่ละตาจึงใช้ transposition ของกันไม่ได้ ทั้งที่หมากฮอสมี transposition เยอะ
   และแต่ละ worker ได้ TT เพียง 1/12
4. **overhead จาก Python ต่อการเรียก** (ThreadPoolExecutor + ctypes และเริ่ม child search ใหม่ทุก depth)
   ledger วัดได้ราว 30–35 ms ต่อการค้นหนึ่งตา จึงเห็นผลชัดที่เวลาสั้น ซึ่ง 1T ชนะ +81
5. **เพดานฮาร์ดแวร์** [ประเมิน]: 6 คอร์จริง 12 logical
   SMT มักให้ราว 1.2–1.3 เท่าต่อคอร์ ดังนั้น SMP ที่ดีที่สุดบนเครื่องนี้น่าจะได้ราว 6–8 เท่าของ NPS 1T ยังไม่ได้วัด

## 3. ทำไมที่ผ่านมาแก้แล้วไม่เห็นผล

- **แก้บน root split ทุกครั้ง**: selective root, root alpha, iterative session, persistent resume,
  private root scheduler, fail-high re-search clear ทุกตัวยังคงโครงสร้าง root split ไว้
  จึงแก้ข้อ 1–3 พร้อมกันไม่ได้
- **ใช้เกณฑ์ที่ shared-TT SMP ผ่านไม่ได้โดยธรรมชาติ**: native root-SMP ที่ใช้ shared TT (2026-08-23)
  ถูกตัดเพราะ 2–12 เธรดได้ผลซ้ำแค่ 1/8 ตำแหน่ง แต่ SMP แบบ shared TT ของ Stockfish
  ก็ไม่ deterministic เมื่อมีมากกว่า 1 เธรดเหมือนกัน เกณฑ์นี้จึงไม่เหมาะกับดีไซน์แบบนี้
  แต่ตัวนั้นยังมีปัญหาอื่นด้วย คือใช้ lock 4,096 ตัวใน hot path และยังเป็น root task ที่ต้องรอกันทุก depth
- **Lazy SMP ใน PR #25 แชร์แค่ move hints แต่ TT ยังแยก**: ข้อดีหลักของ Lazy SMP
  (เธรดได้ใช้คะแนนและ bound ที่เธรดอื่นค้นไว้แล้ว) จึงหายไป ถูก mark `REJECT_FOR_PERFORMANCE`
  และยังติด TSan coverage gate ใน PR #26
- **TT แบบ lockless ของ Stockfish มี race ที่ตั้งใจให้เกิด** แล้วใช้การตรวจ key กันข้อมูลเสีย
  ถ้าจะให้ผ่าน TSan ต้องอ่านเขียนเป็น 64-bit relaxed atomics ไม่ใช่ lock

## 4. ทางแก้ที่เสนอ: Lazy SMP แบบ Stockfish (ทั้งหมดอยู่ใน C)

- ทุกเธรดค้นจาก root ด้วย iterative deepening และ PVS ชุดเดียวกับ 1T ไม่มีจุดรอระหว่าง depth
- shared TT ก้อนเดียว 512 MiB แบบ lockless (เขียน entry เป็น 64-bit relaxed atomics และตรวจ key ตอนอ่าน)
- helper threads กระจาย depth (เช่นข้ามบาง depth ตามลำดับเธรด) เพื่อไม่ให้ค้นซ้ำกันเป๊ะ
- history, killer และ stack แยกต่อเธรด main thread คุมเวลาและเลือกผล
- Python เรียกครั้งเดียวต่อการค้น ไม่ต้องเรียกต่อตาที่ root

เกณฑ์ใหม่ที่ประกาศก่อนวัด
- 1T ต้อง bit-exact กับเอนจิ้นเดิม (move, score, nodes, PV)
- ≥2T ไม่ใช้ determinism เป็นเกณฑ์ ใช้ time-to-depth และ NPS scaling ที่ 1/2/4/6/12 เธรด
  บนชุดตำแหน่งหลายแบบ แล้วตามด้วย SPRT 12T เทียบ 1T ที่ 10 s + 0.1 s
- TSan ต้องสะอาด โดยใช้ atomics ไม่ใช้ lock
- ทุกตาที่ส่งออกต้องถูกกฎ และหยุดตามเวลาได้

## 5. การวัดที่ต้องทำ (เฉพาะช่วงที่ไม่มี gate)

- **M1 เพดานฮาร์ดแวร์** (~15 นาที): รันเอนจิ้น 1T พร้อมกัน 1/2/4/6/8/12 process แล้ววัด NPS ต่อ process
  ถ้ารวมได้ต่ำกว่า ~5 เท่า เพดานของ SMP บนเครื่องนี้จะต่ำ
- **M2 ต้นแบบ Lazy SMP**: ผ่าน 1T parity → scaling → SPRT 12T เทียบ 1T

## 6. ผลที่คาดหวัง [ประเมิน]

ถ้า M1 ได้ราว 6 เท่า และ Lazy SMP มีประสิทธิภาพ 60–70% จะค้นได้ลึกขึ้นราว 1.5–2 ply ที่ 1 วินาที
แผน STRENGTH_PHASE_01 ข้อ 2 ระบุไว้แล้วว่านี่น่าจะเป็นแหล่ง Elo ใหญ่ที่สุดที่เหลือใน production
ตัวเลข Elo ยังประเมินไม่ได้จนกว่าจะมีผล M1/M2
