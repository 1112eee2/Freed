# DRAUGHTS_IDEAS: ไอเดียจากเอนจิ้นหมากฮอสฝรั่งที่ยืมมาใช้กับหมากฮอสไทยได้

ร่าง 2026-10-16 (งานวิจัยที่เจ้าของขอ ต่อจาก [SF_IDEAS_TH.md](SF_IDEAS_TH.md)) สถานะ: **backlog ยังไม่มีอะไรถูกวัด**
ทุกข้อเป็นสมมติฐานจนกว่าจะผ่าน screen → W1 (→ W2) ตามกติกาเดิม

## ทำไมต้องดูฝั่งนี้เพิ่ม

Stockfish เก่งเรื่องโครงสร้างการค้นหาและกระบวนการทดสอบ แต่เกมตระกูลหมากฮอสมีลักษณะที่หมากรุกไม่มี
เช่น การบังคับกินทำให้ตาส่วนใหญ่มีทางเลือกน้อย, จังหวะ (tempo) และ zugzwang สำคัญ, เกมเสมอบ่อยมาก
และท้ายเกมแก้ได้ด้วยฐานข้อมูล เพราะมีหมากแค่สองชนิด เอนจิ้นที่ดูมีสามสาย

- **Chinook** (หมากฮอสอังกฤษ 8×8, มหาวิทยาลัยอัลเบอร์ตา): แก้เกมได้ในปี 2007 ผลคือเสมอ
  ใช้ฐานข้อมูลท้ายเกม 10 ตัว, opening book และการพิสูจน์บนต้นไม้
- **Cake (Martin Fierz) และ KingsRow (Ed Gilbert)** (หมากฮอสอังกฤษ และ KingsRow ทำ 10×10 ด้วย):
  ใช้ eval แบบ pattern หรือ neural net, ฐานข้อมูลท้ายเกม (KingsRow 10 ตัว: WLD, DTW, MTC)
  และ opening book ที่สร้างอัตโนมัติ
- **Scan (Fabien Letouzey)** (หมากฮอสสากล 10×10, โค้ดเปิด): ชนะ Computer Olympiad หลายครั้ง
  eval เป็น pattern ที่เรียนรู้จากการเล่นกับตัวเอง โดยเริ่มจากความรู้แค่ "ฮอส 1 ตัว = เบี้ย 3 ตัว"

## กติกาของเราต่างจากเกมเหล่านี้ตรงไหน (ดู `RULESET.json`)

| เรื่อง | หมากฮอสไทย | อังกฤษ | สากล / รัสเซีย |
|---|---|---|---|
| กระดาน / เบี้ยต่อฝ่าย | 8×8 / 8 ตัว (2 แถว) | 8×8 / 12 ตัว | 10×10 / 20, 8×8 / 12 |
| ฮอส | เดินไกล แต่กินแล้วต้องลงช่องถัดไปทันที | เดินทีละช่อง | เดินไกล ลงได้หลายช่อง |
| เบี้ยกิน | ข้างหน้าเท่านั้น | ข้างหน้าเท่านั้น | ทั้งหน้าและหลัง |
| บังคับกินมากสุด | ไม่บังคับ | ไม่บังคับ | สากลบังคับ / รัสเซียไม่ |

ข้อสรุป: เราใกล้หมากฮอสอังกฤษในเรื่องตัวเบี้ยและขนาดกระดาน และใกล้รัสเซียในเรื่องฮอสเดินไกล
แต่หมากของเรามีน้อยกว่าทุกเกม (16 ตัวตอนเริ่ม) ฐานข้อมูล 6 ตัวของเราจึงครอบคลุมราว 37% ของหมากเริ่มต้น
ส่วน KingsRow ครอบคลุม 10 จาก 24 ตัว (42%)

## สิ่งที่ตรวจในโค้ดเราแล้ว (`native/makhos_native.c` บน search-int-01)

- null move ใช้เมื่อ depth ≥ 3, ไม่มีตากิน, หมาก > 6 ตัว, ไม่ซ้ำตำแหน่ง
  หลักฐานของเราสอดคล้องกับคำเตือนของวงการหมากฮอส ("null move อันตรายเพราะ zugzwang") ทั้งสองด้าน
  - **null move ยังช่วยในภาพรวม**: การปิดหรือลด null move ไม่ผ่าน screen
  - **แต่ใช้แบบไม่ระวังเสียไปเยอะ**: NULL_EVAL_01 (W2 +55.5 Elo) ไม่ได้เพิ่ม null move
    แต่เพิ่มเงื่อนไขให้ลองเฉพาะ null-window node ที่ static eval ≥ beta และไม่ใกล้คะแนน mate
    คือใช้ null move **น้อยลง** เฉพาะตอนที่คาดว่าจะ fail high จริง
  ทางต่อไปจึงเป็นการระวังเพิ่มอีกขั้นด้วยการ **ยืนยัน** null move ไม่ใช่การเอาออก (ดู E2)
- การค้นหาหลักยังไม่มี extension ใด ๆ (มีแค่ fast path ใน qsearch เมื่อมีตากินตาเดียว)

## รายการไอเดีย

ระดับความคาดหวังเป็น [ประเมิน] ทั้งหมด

| # | ไอเดีย (ที่มา) | ปรับให้หมากฮอสไทยยังไง | คาดหวัง |
|---|---|---|---|
| E1 | **ตาบังคับไม่กินความลึก** (เอนจิ้นหมากฮอสทั่วไป) | เป็นรูปแบบที่แรงกว่า S6 ของ Track D: เมื่อมีตาถูกกฎตาเดียว (มักเป็นตากินบังคับ) ให้ค้นต่อโดยไม่ลด depth จำกัดจำนวนครั้งต่อเส้นเพื่อกันการค้นระเบิด **รวมกับ S6 เป็น flag เดียว** ไม่ทำซ้ำ | **กลาง–สูง** (เรายังไม่มี extension เลย) |
| E2 | **Verified null move** (ข้อเสนอในวงการหมากฮอสสำหรับปัญหา zugzwang) | เก็บ null move ไว้ แต่ที่ depth สูง ก่อนรับ cutoff ให้ค้นตำแหน่งจริงซ้ำที่ depth ลดลงเพื่อยืนยัน หรือยืนยันเฉพาะเมื่อโครงสร้างปิด (เบี้ยเดินได้น้อย) ซึ่งเป็นจุดที่ zugzwang เกิดบ่อย | กลาง |
| E3 | **Pattern evaluation** (Scan, Cake, KingsRow) | แบ่งกระดานเป็นบริเวณที่ซ้อนกัน แต่ละช่องมี 5 สถานะ (ว่าง, เบี้ยเรา, เบี้ยเขา, ฮอสเรา, ฮอสเขา) แล้วเรียนรู้น้ำหนักต่อรูปแบบด้วย logistic regression โดยใช้คะแนนจากการค้นเป็น label (มีรายงานว่าดีกว่าใช้ผลแพ้ชนะ) Cake ใช้ 1/4 ของกระดาน (8 ช่อง, 5⁸ แบบ) กระดานเราเล็กและมีหมากสองชนิด จึงเหมาะกับ pattern แต่ Letouzey เตือนว่าหมากที่เดินไกล (ฮอส) ทำให้ pattern แย่ลง ใช้ได้สองแบบ: เป็นตัวเทียบราคาถูกกับ NNUE v1 หรือเป็น input เสริมของ NNUE | กลาง (NNUE เรามีแล้ว คุณค่าอยู่ที่การวินิจฉัยและ hybrid) |
| E4 | **ความรู้หมากฮอสคลาสสิก** (eval แบบมือของ Chinook/Cake) | ตรวจว่า NNUE เห็นสิ่งเหล่านี้ไหม: เบี้ยที่ไปถึงแถวฮอสได้โดยไม่มีใครขวาง (runaway man), การนับ tempo, การคุมแถวหลัง, ฮอสที่ถูกขัง ใช้ชุด collapse ของ C1 วัดว่าตาที่ทรุดตรงกับเรื่องไหน ถ้า NNUE ไม่เห็น ให้ใส่เป็น feature ใน NNUE v3 หรือเป็น extension (เช่นค้นต่อเมื่อมี runaway man) | กลาง |
| E5 | **Opening book แบบ drop-out expansion** (Lincke; Cake, Chinook) | สร้าง book อัตโนมัติด้วยการค้นลึก แล้วขยายโหนดที่คะแนนใกล้ทางหลักที่สุดก่อน จนได้ต้นไม้ที่ครอบคลุมทุกตาที่มีโอกาสเล่น ใช้ต่อยอด C3 และเป้าหมายเสมอเกือบ 100% ใน self-play ป้ายกำกับยังเป็น "ตรวจด้วยการค้นลึกที่ depth/เวลา X" | กลาง–สูง (สำหรับเป้าไม่แพ้ ไม่ใช่ Elo) |
| E6 | **ชุดเปิดเกมแบบ ballot** (หมากฮอสอังกฤษ 3-move ballot) | แจกแจง opening ทุกแบบที่ N ply ค้นลึกเพื่อตัดแบบที่แพ้แน่ ("barred ballot") ทิ้ง แล้วคัดแบบที่สมดุลแต่ไม่แห้ง ใช้แทนหรือเสริม T3 (UHO) ทำให้ SPRT เสมอน้อยลงและตัดสินเร็วขึ้น เปลี่ยนเฉพาะก่อนเริ่ม run ใหม่ | กลาง (ประหยัดเวลาเครื่อง) |
| E7 | **ฐานข้อมูลท้ายเกมใหญ่ขึ้นและแบบ DTW/MTC** (KingsRow) | TB7 อยู่นอก scope ของ practical no-loss track ตอนนี้ ต้องให้เจ้าของอนุมัติใหม่ เป็นงาน V3 ส่วนที่ทำได้ก่อนคือตรวจว่าเอนจิ้นปิดเกมที่ TB บอกว่าชนะได้จริงก่อน 80 ply ไหม ถ้าไม่ได้ ค่อยพิจารณาข้อมูลแบบ depth-to-conversion | ต่ำ (ตอนนี้) |

### ไม่ทำตอนนี้

- **การพิสูจน์ opening แบบ Chinook** (proof tree, DFPN): scope ปัจจุบันตัดงาน proof/DFPN ออก
- กติกาบังคับกินมากสุด, เบี้ยกินถอยหลัง, ช่องลงหลายช่องของฮอส: เป็นของเกมอื่น เทคนิคที่ผูกกับกติกาเหล่านี้ใช้ไม่ได้

## ลำดับที่เสนอ

1. **ไม่แทรก A2/A4 หรือ RC-2**: เขียนโค้ดได้ระหว่าง gate แต่วัดเฉพาะช่วงที่ไม่มี gate
2. **E1** (รวมกับ S6) และ **E2** แยก flag ปิดค่าเริ่มต้น เข้าคิวหลัง D1–D3
3. **E6** เตรียมชุดเปิดเกมระหว่างรอ ใช้กับ run ชุดถัดไปหลัง RC-2 เท่านั้น
4. **E5** ทำคู่กับ C3 หลัง RC-2
5. **E3/E4** เป็นงานวิจัยของ NNUE v3 (E4 เริ่มจากการวิเคราะห์ชุด collapse ได้ก่อน เพราะใช้เครื่องน้อย)
6. **E7** รอเจ้าของตัดสิน scope
